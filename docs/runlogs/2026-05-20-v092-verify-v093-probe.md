Two back-to-back read-only passes on the same cold-booted Hurd 0.9 VM.
Pass one re-verifies that the Hurd backend in `core/network.el` shipped
at main/ccfd06d parses what the live kernel actually emits. Pass two is
a scoping probe for v0.9.3: the disks buffer and the install wizard's
disk surface, both currently Linux-only. The image identifies itself as
`GNU geos-hurd 0.9 GNU-Mach 1.8+git20260224-up-amd64/Hurd-0.9 x86_64
GNU`, Debian forky/sid, reached over ssh on 127.0.0.1:2222 as root.

The canonical "long-running" VM was not actually up at the start of the
session. With explicit go-ahead, a snapshot of
`/home/overdrive/hurd-vm/work.img` was copied to
`/tmp/geos-hurd-vm-v092v093.img`, cold-booted, probed, and torn down.
The canonical image was not touched; its mtime is still May 18 13:34
at the end of this receipt. QEMU shape that worked was
`qemu-system-x86_64 -enable-kvm -cpu host -drive if=ide ...`. The first
attempt (TCG, virtio, no `-enable-kvm`) hung silently for ten minutes
and was killed. Cold boot to ssh-ready on the working shape was about
sixty-one seconds.

## Verdict

v0.9.2 VM-verify: PASS on shape, INCONCLUSIVE on the flags-base
question. The live `/proc/route` matches the format the parser was
written for, decimal-dotted addresses and `/dev/<iface>` in the Iface
column. `/proc/net/route` confirmed absent. The `/dev/` prefix strip
and decimal pass-through are exercised on real data. The flags column
on this VM only ever shows `0001` and `0003`, the same two values the
original scoping probe saw, so the hex-vs-decimal question for the
flags field is NOT decisively answered here. The parser defaults to
hex per the Linux convention and the `%04X` zero-padded shape; that
inference is now filed honestly in the parser docstring as an open
inference until a future probe synthesizes a route with a flags value
that disambiguates (e.g. `0005` or `0010`).

v0.9.3 probe: scoping data captured. The Linux-style block-device
enumeration path does not transfer: `/proc/partitions` and
`/proc/diskstats` are both absent, `/sys/block` is absent, and the
device-column shape in `/proc/mounts` is Hurd-native, not `/dev/sdaN`.
`parted` and `sgdisk` are not installed; `fdisk`, `sfdisk`, `blkid`,
`mkfs.ext{2,4}`, and `grub-install` are. The disks buffer and the
install wizard's enumeration step can ship on a `/dev/` walk plus
`/proc/mounts` parse; the wizard's partition/format/grub steps need
real thought because the tool surface is different from Linux.

### What this proves and what it does not

The parser's input shape matches reality: leading `/dev/` on the Iface
column, decimal-dotted Destination/Gateway/Mask, the same 11-column
header the Linux side has. The `/dev/` strip path and the
decimal-address pass-through both run on real data here.

What this does NOT prove: the flags column on this VM only ever shows
`0001` and `0003`. Both values parse identically under hex and
decimal interpretation (no digit `>= a` and no leading `0` strip that
would change meaning). A flags value like `0005` (RTF_UP + RTF_HOST)
or `0010` (RTF_MTU) would be needed to tell the two interpretations
apart. The parser defaults to hex, matching the Linux `%04X` shape,
and the docstring now flags this as an open inference. If a future
probe catches it parsing wrong, flip the base in
`network--read-proc-net-route-hurd`.

## Verdicts (v0.9.3 surface)

- `/proc/partitions`, `/proc/diskstats`: ABSENT on Hurd procfs. The
  disks buffer cannot use the Linux block-device enumeration path on
  Hurd; needs a `/dev/` walk for the conventional Hurd patterns (`wd`,
  `hd`, `sd`, `ucd`, `ud`, `cd`, `fd`).
- `/proc/mounts`: PRESENT and parseable, but the device column is
  Hurd-native, either the literal `/dev/wd0s2` node OR a translator
  argv referencing `part:N:device:disk`. `install-disk-mounted-p`
  needs new matching logic since `/dev/sda1`-prefix matching does
  not transfer.
- `/sys/block`: ABSENT (no sysfs on Hurd). Size, model, removable
  fields all need an alternative source or honest nil returns.
- Tooling: `mkfs.ext2`/`mkfs.ext4`, `fdisk`, `sfdisk`, `grub-install`,
  `blkid` all present. `parted` and `sgdisk` are NOT installed; the
  wizard's partition step needs `fdisk`/`sfdisk` instead, or
  `parted` shipped as a profile dependency.
- Hurd-specific surfaces for native enumeration: `/hurd/storeio`
  exposes block devices as translators. `fsysopts <node>` reads the
  live translator argv (`part:N:device:disk` for partitions).
  `device_get_status()` Mach RPC against the storeio port would give
  byte size and other properties; that is `port_hurd.c` work, not
  elisp.

## Recommendation for v0.9.3 scoping

Tier A, cheap, text-only, ships first:

- Disks buffer: walk `/dev/` for the Hurd disk-node patterns, parse
  `/proc/mounts` for the mounted-on column. Size renders `?` for
  unmounted devices (no sysfs equivalent), df-derived for mounted
  partitions. No `/servers` walking, no `storeio` shell-out.
- `install/disk.el`: enumerate the same way, whole-disk patterns only,
  skip the `wd0s*`-style partition nodes since the wizard installs
  onto a whole disk. `install-disk-mounted-p` parses `/proc/mounts`
  and matches both the literal `/dev/wd0sN` device string and the
  `part:N:device:wd0` translator-arg form. The downstream wizard
  steps (partition with `parted`, mkfs, grub-install for i386-pc) do
  NOT port cleanly: parted is absent, grub on Hurd is
  `i386-pc`-only via the patched `hurd.1` build, and the flow needs
  serious thought. Document the wizard as "enumeration-ready on
  Hurd, partition/format/grub steps deferred to a later slice".

Tier B, Mach-RPC, later:

- `device_get_status` via the storeio port for size, model, removable
  surface.
- An install-on-Hurd-from-Hurd partition/format/grub flow that uses
  `fdisk`/`sfdisk` instead of parted.

## Out of scope

- IPv6 surface (`/servers/socket/26`) for network counters, deferred
  to v0.9.3+.
- Per-interface byte/packet counters (Tier B, pfinet RPC).
- Audio surface: no `/proc/asound`, no `/dev/dsp`, no `/hurd/*`
  audio translator in the top-thirty `/hurd/` listing.
- Journal source on Hurd: no `/dev/kmsg`. `/dev/console` reads
  possible but a separate slice.
