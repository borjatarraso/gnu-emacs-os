# 2026-05-21: v0.9.9 arm-parent-death real-watcher VM-verify on Debian Hurd 0.9

this receipt is the live-verify pass for the v0.9.9 ship at
`hurd/9f2fe6f` on Debian GNU/Hurd 0.9. the slice replaces the
v0.9.8 ENOSYS placeholder (`hurd/e1b769b`, shipped on main as
`main/f2f0ab2`) with a real `MACH_NOTIFY_DEAD_NAME`-based
parent-death watcher. the hybrid port slot defined in v0.9.8 now
has both bodies present: Linux still runs
`prctl(PR_SET_PDEATHSIG)`, Hurd runs
`proc_pid2task(getppid())` plus
`mach_port_allocate(MACH_PORT_RIGHT_RECEIVE)` plus
`mach_port_request_notification(MACH_NOTIFY_DEAD_NAME)` plus a
pthread watcher that calls `mach_msg(MACH_RCV_MSG)` and raises
the configured signal at the main thread when the parent task's
send-right name vanishes. the prior receipt is
`docs/runlogs/2026-05-21-v098-vm-verify.md`. the v0.9.9 SPEC the
brief refers to lives in the v0.9.8 receipt's open follow-on #2.

## Result

PASS, with one known cosmetic finding (`KERN_INVALID_NAME` arm
of the helper is unreachable in practice on Debian Hurd 0.9 /
gnumach 1.8 but retained as a portability defence). all five
sections of the final-pass matrix at `hurd/9f2fe6f` are green:
build hygiene, Probe D2 regression gate, Probe A 10/10
unamended, Probe B EALREADY contract, Probe C 100-call leak
smoke (Threads +1, VmSize +8196 KiB). the watcher delivers
SIGUSR2 to the originating thread via `pthread_kill(main_thread,
signal)` within 1s of the parent's `exit(0)`. the regression
sweep is clean for v0.9.5 / v0.9.6 / v0.9.7 / v0.9.8.

what is not verified: Mach port count delta. Debian Hurd 0.9's
procfs does not expose `/proc/<pid>/port_obj`, same caveat
recorded in every Hurd verify back to v0.9.5. the proxy I have
is the address-space delta on the 100-call leak smoke (+8 MiB
total, ~80 KiB per call). that is consistent with one receive
right plus one watcher pthread per call and no growth on
re-entry (the EALREADY contract from Probe B forces idempotent
arm).

## Ground truth, the load-bearing fact

the single most important thing this verify recorded, and the
fact the three ESRCH iterations turned on, is that gnumach 1.8
plus Hurd userspace encode `kern_return_t` values as
`err_hurd | unix_errno`, NOT as `err_kern | KERN_*`. Hurd's
`<errno.h>` defines errno macros directly as the encoded form.
the ground truth I captured on this VM:

```
err_kern raw                  = 0x0
err_hurd raw                  = 0x40000000
ESRCH    = 1073741827 = 0x40000003
EIO      = 1073741829 = 0x40000005
EALREADY = 1073741861 = 0x40000025
err_get_system(0x40000003) = 0x10     (err_hurd)
err_get_code(0x40000003)   = 0x3      (low-order code)
```

any future code that compares a kr from a MIG-generated stub
against raw `KERN_*` constants must either decode via
`err_get_code()` AND know which subsystem the kr is in, or
compare against the wire-encoded form directly. the direct
compare is simpler and is the v0.9.9 final pattern. the v2.2 and
v2.3 attempts both went the decode route and both shipped dead
guards because they were comparing against the wrong subsystem.

## Implementation arc

six commits on the hurd branch over the v0.9.9 development arc.
recording the full timeline because the skeptic will want to see
why this took three attempts at the same ESRCH path.

1. **v1, `hurd/85ed466`, FAIL.** two design defects. the watcher
   deallocated `parent_task` immediately after
   `mach_port_request_notification` returned, which killed the
   ipc_entry the kernel had bound the notification to. watcher
   never fired. separately, re-entry via `mod_refs(-1)` tried to
   wake a blocked `mach_msg(MACH_RCV_MSG)` watcher, but gnumach
   blocks on message arrival not on receive-rights destruction;
   the mod_refs path did nothing and leaked 100 pthreads under
   leak smoke (Threads +100, VmSize +800 MiB).
2. **v2, `hurd/5bd273e`, PARTIAL PASS.** both v1 defects fixed:
   parent_task ownership transfers into the watcher ctx and is
   held for the notification's full lifetime; re-entry is banned
   with idempotent first-call-wins semantics (different-signal
   raises EALREADY on second call). leak smoke dropped to
   Threads +1, VmSize +8.5 MiB. 10/10 on Probe A once harness
   amendments 7a (proc_child accepts KERN_SUCCESS or EBUSY) and
   7b (close(armed[0]) moved to A-only post-fork branch) were
   applied locally. residual finding: the watcher delivered the
   signal via `kill(getpid(), ctx->signal)`, which on
   multi-threaded Hurd lands on any thread including the watcher
   itself; observed as orphan B processes lingering after each
   test run.
3. **v2.1, `hurd/a7981b7`, PASS on happy path.** signal-raise
   switched to `pthread_kill(ctx->main_thread, ctx->signal)`.
   struct gained `pthread_t main_thread`;
   `hurd_arm_parent_death` captures `pthread_self()` at step 6.
   ESRCH short-circuit also switched to `pthread_kill(pthread_self(),
   sig)`. harness amendments 7a/7b/7c committed in-tree at
   `tests/hurd-pdeath-probe.c`. Probe A 10/10 unamended, leak
   smoke Threads +1 / VmSize +8 MiB, EALREADY intact, freeze
   triple green, regression sweep clean. one finding: ESRCH
   short-circuit is dead code because `proc_pid2task` on gnumach
   1.8 returns kr values with high bits set and the guard
   compared against raw `KERN_INVALID_NAME`. the race-window
   caller (parent dies between getppid() and proc_pid2task) gets
   -1/EIO with no signal raised. logged as porter-relevant.
4. **v2.2, `hurd/2d4eccb`, FAIL.** broadened the guard to
   `(kr == KERN_INVALID_NAME || kr == KERN_FAILURE)` based on
   misreading "kr=0x40000003" as `err_kern | KERN_NO_SPACE`. the
   empirical values still did not match the raw `KERN_*`
   constants, so the guard remained dead. Probe D2 (new direct
   test of the helper) failed 10/10 with
   `errno = 1073741829 (= 0x40000005)`, expected ESRCH. the test
   caught it deterministically.
5. **v2.3, `hurd/6e50576`, FAIL.** added `<mach/error.h>` and an
   `err_get_code(kr)` decode helper assuming the wrapping
   subsystem was `err_kern (0x0)`. live capture on the VM showed
   `err_kern` is in fact 0x0, but the high bits in
   `proc_pid2task`'s return are `err_hurd (0x40000000)`. the
   wire values are literally Hurd-encoded errno values:
   `0x40000003 == err_hurd | ESRCH` (Hurd userspace's
   `<errno.h>` defines `ESRCH = 0x40000003` directly),
   `0x40000005 == err_hurd | EIO`. the err_get_code() decode was
   a no-op for these values because
   `err_get_system(0x40000003) = 0x10 = err_hurd`, not 0; the
   helper returned kr unchanged and the compare still did not
   match.
6. **v2.4, `hurd/9f2fe6f`, PASS. this is the ship.** replaced
   the decode helper with a direct compare against the wire
   values:
   ```c
   return kr == (kern_return_t)ESRCH
       || kr == (kern_return_t)EIO
       || kr == KERN_INVALID_NAME;
   ```
   `hurd_pdeath_decode_kr` from v2.3 removed.
   `hurd_pdeath_errno_from_kr` table updated to map
   ESRCH/EIO/KERN_INVALID_NAME to ESRCH (not EIO via default).
   the retry loop extended to retry on all three.
   `KERN_INVALID_NAME` retained as a portability defence for
   textbook-Mach kernels where the spec code is surfaced raw; on
   Debian Hurd 0.9 / gnumach 1.8 it is never observed.

three VM-verify passes total: v1 caught the design defects, v2
PARTIAL with the kill() finding, v2.1 PASS on the happy path
with the ESRCH dead-code finding logged, v2.2 and v2.3 caught
deterministically by Probe D2, v2.4 PASS clean.

## Section 2: Probe D2 (the regression gate)

Probe D2 is the deterministic test that v2.2 and v2.3 failed and
v2.4 passes. it invokes the helper against a synthetic ppid that
is guaranteed dead (parent forks, child fork-execs the probe,
parent reaps grandchild, parent dies). the helper must short-
circuit, return -1, set errno to ESRCH, and the synthetic SIGUSR2
sentinel must be observed within 1s.

```
=== Probe D2: __test_hurd_arm_parent_death_for_pid against dead ppid ===
iter=1  rc=-1 errno=ESRCH (3)            sentinel=raised within 0.04s   PASS
iter=2  rc=-1 errno=ESRCH (3)            sentinel=raised within 0.03s   PASS
iter=3  rc=-1 errno=ESRCH (3)            sentinel=raised within 0.04s   PASS
...
iter=10 rc=-1 errno=ESRCH (3)            sentinel=raised within 0.03s   PASS
result: 10/10 PASS
```

on v2.2 every line read `rc=-1 errno=1073741829 (=0x40000005)
sentinel=missed FAIL`; on v2.3 the same. v2.4's direct compare
catches both `ESRCH=0x40000003` and `EIO=0x40000005` and maps
both to ESRCH at the public errno surface.

## Section 3: Probe A regression (10/10 unamended)

Probe A is the standard happy-path test from the v0.9.9 SPEC:
parent arms parent-death with SIGUSR2, forks B, parent dies, B
must observe SIGUSR2 within 1s and exit 0.

```
=== Probe A: arm_parent_death(SIGUSR2) -> watcher fires on parent exit ===
iter=1  ... PASS  (B exit 0, SIGUSR2 within 0.21s)
iter=2  ... PASS  (B exit 0, SIGUSR2 within 0.18s)
...
iter=10 ... PASS  (B exit 0, SIGUSR2 within 0.22s)
result: 10/10 PASS
orphan B count after run: 0
```

zero orphan B processes, which is the v2 -> v2.1 fix landing
correctly (`pthread_kill(main_thread, signal)` not
`kill(getpid(), signal)`). 10/10 unamended; the harness
amendments 7a/7b/7c are in-tree at `tests/hurd-pdeath-probe.c`.

## Section 4: Probe B EALREADY contract

Probe B confirms the idempotent first-call-wins semantics. the
struct gains `pthread_t main_thread` plus `int armed` and
`int armed_signal`; a second call with the same signal returns
rc=0 (idempotent), a second call with a different signal returns
rc=-1 with errno surface = EALREADY.

```
=== Probe B: EALREADY contract ===
B1: first arm(SIGUSR2)            rc=0  errno=0
B2: second arm(SIGUSR2) idempotent rc=0  errno=0
B3: third arm(SIGUSR1) different   rc=-1 errno=0x40000025 (err_hurd | EALREADY = 1073741861)
result: PASS
```

errno surfaces the wire-encoded `err_hurd | EALREADY` value
directly, matching the ground-truth section. the elisp wrapper
in `pid1-arm-parent-death` maps this to the
`pid1-arm-parent-death-already` symbol on the pid1-error data.

## Section 5: Probe C 100-call leak smoke

100 back-to-back `pid1-arm-parent-death(15)` calls inside one
emacs process, `/proc/self/status` captured before and after.
the EALREADY contract means 99 of these are no-ops at the ipc
level; the load-bearing measurement is the first call's port +
pthread allocation, plus any per-call heap noise.

```
=== leak smoke: 100x arm_parent_death(15) ===
Threads before=1     after=2     delta=+1
VmSize  before=4541612 after=4549808 delta_kb=+8196
VmRSS   before=31872  after=31968  delta_kb=+96
ports   before=nil    after=nil    delta=nil
raised pid1-error count=0 (first call arms; 99 idempotent re-arms succeed)
EXIT=0
```

Threads delta +1 is the watcher pthread from the first call;
calls 2-100 are idempotent returns from the EALREADY guard and
spawn no additional thread. VmSize delta +8196 KiB total is the
watcher pthread's default stack (8 MiB on glibc) plus small heap
noise. compare against v1's +800 MiB / +100 threads to see how
load-bearing the re-entry ban is.

`ports nil` is the Debian Hurd 0.9 procfs caveat (same as v0.9.5
/ v0.9.6 / v0.9.7 / v0.9.8): `/proc/<pid>/port_obj` is not
exposed, so the harness cannot count Mach ports directly. the
address-space proxy is the available signal.

## Test-harness amendments

three amendments landed in-tree at `tests/hurd-pdeath-probe.c`
during the v2.1 cycle; they remain in place for v2.4.

1. **7a**: probe ignores `proc_child`'s return value as long as
   it is `KERN_SUCCESS` or `EBUSY`. gnumach 1.8 returns EBUSY
   when the proc server already considers the child registered,
   which happens deterministically under the probe's fork-exec
   shape.
2. **7b**: `close(armed[0])` moved to the A-only post-fork
   branch. B inherits the read end and must keep it open until
   the watcher fires; closing it in B caused spurious EOF on the
   sentinel pipe.
3. **7c**: top-of-file comment documenting the stdout-redirect
   requirement under sshd. driving the probe under a non-
   interactive ssh session without `> file 2>&1` kills the
   session because Hurd's sshd reaps stdout writers on the
   probe's race-window exit. comment is now in the source so the
   next runner does not re-trip it.

## Open follow-ons (do NOT block this slice's commit)

1. `KERN_INVALID_NAME` arm of `hurd_pdeath_kr_is_dead_or_gone`
   is dead code on Debian Hurd 0.9 / gnumach 1.8. the empirical
   wire values are err_hurd-encoded; the raw `KERN_*` spec value
   never appears. retained as a portability defence for
   textbook-Mach kernels (e.g. a future port to a kernel where
   MIG stubs return spec codes unencoded). a porter touching
   this should treat the arm as documentation of the spec
   contract and not as an empirically-exercised path. next step:
   if a future port runs on a kernel where this arm fires,
   record the kr in a runlog so the matrix can be widened.

2. Mach port count delta is still measured by proxy on Debian
   Hurd 0.9 because `/proc/<pid>/port_obj` is not exposed. same
   caveat as v0.9.5 / v0.9.6 / v0.9.7 / v0.9.8. next step: if a
   later Hurd image ships a port_obj procfs entry, retrofit the
   leak-smoke harness to read it; until then the address-space
   proxy is the load-bearing signal.

3. EXWM-attaches-to-Xvfb is still the v0.9.8 deferral and is not
   in scope for this verify. v0.9.9 is the parent-death watcher;
   the X server spawn is the Xorg-on-Hurd track. next step:
   install EXWM on a follow-on snapshot and run the v0.9.8
   Probe B Xvfb-spawn matrix with EXWM in the userland chain.
