# 2026-05-30 v0.9.22 slice B done, full 35-file init.args boots to SSH

Continuation of docs/runlogs/2026-05-30-hurd-v0921-efficiency-triple.md.
v0.9.22 closes task #220 (the slice B canonical 35-file init.args bake)
by correcting the v0.9.21 misdiagnosis: what three release cycles called
a "rumpdisk wd0 enumeration race" was not a race at all. It was a flat
missing-driver bug. Hurd's rumpdisk has no virtio-blk driver, so
`-drive if=virtio` cannot enumerate the disk at all and ext2fs wedges
on "part:2:device:wd0: No such device or address". `-drive if=ide`
enumerates the disk as wd0 at atabus0 drive 0 via piixide, which
rumpdisk does drive, and ext2fs mounts cleanly first try.

The same investigation also turned up a sibling missing-driver bug in
Hurd's netdde: virtio-net-pci is not driven either, so `-device
virtio-net-pci` reproducibly takes pfinet settrans to exit=4 and the
sshd we autostart has no IPv4 routing. `-device e1000` binds to netdde
cleanly and brings settrans to exit=0.

Both flips landed in iso-build/hurd-image-reroll.sh and
iso-build/hurd-fast-iterate.sh. The slice B 35-file init.args HEREDOC
that v0.9.20 wrote back in main/06fe... and that v0.9.21 reverted is
now restored as the canonical bake.

## Triple-control isolation that misled v0.9.21

The v0.9.21 receipt described a "deterministic rumpdisk wd0
enumeration race that reproduces on the known-good v0.9.20 image" and
called it "100% reproducible on this host". That framing was correct
about the reproducibility and wrong about the root cause. The triple
control (NOT slice B, NOT qcow2, NOT v0.9.21 mutations) did establish
that the wedge lives in the canonical pristine's boot configuration,
not in any GEOS change. What the control did NOT do was vary the QEMU
storage backend, which is where the actual variable lived. With
`-drive if=virtio` every triple-control combination wedges. With
`-drive if=ide` every triple-control combination boots clean.

Lesson recorded for future verify cycles: when a Hurd boot wedges
before init runs, vary `-drive if=` and `-device` first before
declaring an upstream race in gnumach. Hurd's PCI driver coverage in
rumpdisk and netdde is narrow.

## How v0.9.22 boots, observed line by line

Live serial from the foreground boot used to verify SSH (e1000,
if=ide qcow2 overlay):

```
pid1: /run/sshd 0755 ready (openssh privsep chroot)
hurd-essentials: file loaded, geos-kernel=hurd
hurd-essentials: geos-kernel=hurd gate passed, registering services
hurd-essentials: defservice hurd-sshd + hurd-syslogd registered
hurd-essentials: settrans /hurd/pfinet -i /dev/eth0 -a 10.0.2.15 -m 255.255.255.0 -g 10.0.2.2
hurd-essentials: settrans pfinet exit=0
hurd-essentials: eth0 static skipped, pid1-set-address unbound
supervise: autostart name=hurd-sshd
supervise: spawn name=hurd-sshd cmd=("/usr/sbin/sshd" "-D" "-e")
supervise: spawn name=hurd-sshd pid=34 OK
supervise: registry loaded 4 entries
```

`pid1-set-address unbound` is expected and documented: the supervised
emacs at /usr/bin/emacs is the child of pid1, not pid1 itself, so it
does not have the C module symbols. The static address was already
applied via settrans pfinet's -a 10.0.2.15 -m 255.255.255.0 -g 10.0.2.2
arguments; the unbound symbol path is just the elisp-side belt-and-
suspenders that runs after the settrans and short-circuits when the
module symbol isn't available. Network is up either way.

SSH probe from host:

```
$ ssh -i ~/.ssh/geos-hurd-vm.key -p 2266 -o StrictHostKeyChecking=no \
      -o UserKnownHostsFile=/dev/null root@127.0.0.1 'uname -srm'
GNU 0.9 x86_64
```

First attempt, no retry, no banner-exchange timeout.
