# 2026-05-21: v0.9.8 arm-parent-death VM-verify on Debian Hurd 0.9

this receipt is the live-verify pass for the v0.9.8 slice at
`main/f2f0ab2` and the hurd-branch ENOSYS placeholder at
`hurd/e1b769b`. the slice adds a `port->arm_parent_death(int signal)`
slot to pid1's port abstraction. the Linux backend wraps
`prctl(PR_SET_PDEATHSIG)`. the Hurd backend returns ENOSYS as the
v0.9.8 placeholder, with the v0.9.9 follow-on planned to implement
the real `MACH_NOTIFY_DEAD_NAME` watcher (`proc_pid2task` +
`mach_port_allocate` + `mach_port_request_notification` + pthread
watcher). the probe-prior receipt that informed the design lives at
`docs/runlogs/2026-05-21-hurd-xorg-probe.md` (Xvfb works on Hurd,
native Xorg dies on kbd_drv ioctl, `proc_setowner` is deprecated,
`MACH_NOTIFY_DEAD_NAME` is the correct primitive).

## Result

PASS. all five acceptance points met cleanly on Debian GNU/Hurd 0.9.
the Hurd `hurd_arm_parent_death` returns -1/ENOSYS via the documented
ENOSYS-class `pid1-error`. the C-side range guard catches sig=999 and
sig=0 with EINVAL before any port-table dispatch. pid1 boots into UI
mode via the un-forced `GEOS_MODE_UI` path now that the
`#ifdef PORT_HURD ... GEOS_MODE_CONSOLE` override block is gone, and
spawns `/usr/bin/Xvfb` with the documented `is_xvfb` argv. the 100-call
leak smoke is clean: VmSize delta 0, VmRSS delta 40 KiB (~0.4 KiB per
call heap noise, not port growth), all 100 calls deterministically
raised `pid1-error`. regression sweep confirms v0.9.5
(`pid1-disk-size-bytes "wd0"` = 4194304000), v0.9.6
(`services/journal-tail.el` requires clean under `GEOS_KERNEL=hurd`),
and v0.9.7 (`journal-tail--prime-from-dmesg` still doubles 4865 ->
9730 by design).

what is not verified: EXWM attaches to the spawned Xvfb. EXWM is not
installed on this canonical image so the conditional part of the
acceptance is untested. the unconditional Xvfb-stays-up part did pass.
the `/dev/console` boot transcript line also did not surface on the
serial capture because emacs-init routes its console messages to the
Mach console device, not to the QEMU `-serial file:` sink. the literal
"Hurd UI default, spawning /usr/bin/Xvfb" string is present in the
binary (verified by `strings`); the process tree confirms the actual
spawn happened.

## Test-harness amendments

beyond the four amendments already recorded in
`docs/runlogs/2026-05-21-v096-dmesg-prime-verify.md` (panic.el under
`core/`, `journal-buffer.el` symlink to `journal.el`, `state.el`
transitive dep, `GEOS_KERNEL=hurd` env prefix under
`emacs -Q --batch`), this verify recorded two new minor gotchas.

1. `STATIC=0` is required for `make PORT=hurd` on a stock Debian Hurd
   0.9 image. the image does not ship `libc.a` so a STATIC=1 link
   fails at the final cc step. recording so the next verifier does not
   re-trip it.
2. driving `emacs-init` as a non-PID-1 child of an ssh session kills
   the ssh session and leaves Hurd's sshd unresponsive afterwards.
   drive it only inside a screen/tmux-style detachable session, or do
   the boot-mode check via a fresh-snapshot reboot instead of an
   in-place run.

## Probe A: module load + arm-parent-death

drove `pid1-arm-parent-death` under
`GEOS_KERNEL=hurd emacs -Q --batch` with the freshly built
`pid1-module.so` loaded.

```
loading module...
fboundp pid1-arm-parent-death: t
arity: (1 . 1)
--- sig=15 (SIGTERM) ---
caught pid1-error: (pid1-error "pid1: arm-parent-death: Function not implemented")
--- sig=999 (out of range) ---
caught pid1-error: (pid1-error "pid1: pid1-arm-parent-death: signal out of range: Invalid argument")
--- sig=0 (out of range) ---
caught pid1-error: (pid1-error "pid1: pid1-arm-parent-death: signal out of range: Invalid argument")
EXIT=0
```

the Hurd backend returns ENOSYS as documented. the C-side range guard
catches sig=999 and sig=0 with EINVAL before any port-table dispatch.
the signalled class is exactly `pid1-error` in all three cases. the
data shape is `(STRING)` starting with `"pid1: "` and containing the
strerror text. matches what `freeze-test/arm-parent-death-error-shape`
asserts.

## Probe B: pid1 boot into UI mode (Xvfb spawn)

`/etc/geos-cmdline` is absent on the VM, so `read_geos_mode()`
returns `GEOS_MODE_UI` via the new v0.9.8 default-on-absence message
("pid1: /etc/geos-cmdline unreadable, defaulting to ui mode"). the
v0.7.x `#ifdef PORT_HURD ... GEOS_MODE_CONSOLE` override is gone,
confirmed both by source read and by absence of the corresponding
string from `strings emacs-init`. the Hurd UI block ran the
`access("/usr/bin/Xvfb", X_OK)` check (Xvfb was installed before the
run) and committed to `xorg_path = "/usr/bin/Xvfb"`.

process tree ~4s after launch:

```
root  1587   1  /root/pid1-v098/emacs-init
root  1591  1587  /usr/bin/Xvfb :0 -screen 0 1024x768x24 -nolisten tcp -noreset
```

Xvfb has the exact argv `spawn_xorg` builds for `is_xvfb`: no
`-config`, no `-modulepath`, no `-logfile`. those are Xorg-only and
are dropped by the `is_xvfb` branch. the supervisor did not trip
`xorg_disabled` in the observed window. EXWM is not installed on this
image so i cannot confirm EXWM attaches; per the brief that is the
conditional acceptance, and Xvfb-stays-up is the unconditional
acceptance, which is met.

note: `/tmp/Xorg.0.log` did not populate within the 4s window (Xvfb
is silent on a clean idle :0 startup). emacs-init's console messages
route to `/dev/console` (Mach console device), not the QEMU
`-serial file:` capture, so the "Hurd UI default, spawning
/usr/bin/Xvfb" line did not show on the serial transcript. `strings`
on the binary confirms the literal is in place.

side effect, recording for the next verifier: driving `emacs-init` as
a non-PID-1 child of an ssh session kills the ssh session and leaves
Hurd's sshd unresponsive afterwards. drive it only inside a
screen/tmux-style detachable session, or do the boot-mode check via a
fresh-snapshot reboot rather than in-place.

## Probe C: 100-call arm-parent-death(15) leak smoke

drove `(pid1-arm-parent-death 15)` 100 times back-to-back in a single
emacs process, capturing `/proc/self/status` before and after.

```
=== leak smoke: 100x pid1-arm-parent-death(15) on Hurd ===
VmSize before=4538924 after=4538924 delta_kb=0
VmRSS  before=31852 after=31892 delta_kb=40
ports  before=nil after=nil delta=nil
raised pid1-error count=100 (expected 100)
EXIT=0
```

VmSize delta 0: zero address-space growth across 100 calls. VmRSS
delta 40 KiB total, ~0.4 KiB per call. that is heap noise from
symbol/string conversions in the binding's signal path, not a port
leak; an actual leak would show monotonic growth proportional to the
call count. `ports before=nil after=nil delta=nil` because Debian
Hurd 0.9 procfs does not expose `/proc/<pid>/port_obj`; same caveat
the v0.9.5 / v0.9.6 / v0.9.7 verifies recorded. 100/100 raises caught
confirms `hurd_arm_parent_death` reliably returns -1/ENOSYS and the
C-side signal path is deterministic.

scp'd the prior-slice fixtures back onto the VM and re-ran them under
`GEOS_KERNEL=hurd emacs -Q --batch` to confirm v0.9.5/v0.9.6/v0.9.7
contracts still hold.

```
=== load services/journal-tail.el under GEOS_KERNEL=hurd ===

fboundp prime? t
*journal* exists? t size=4865
explicit-prime: before=4865 after=9730 delta=4865
EXIT=0
```

- v0.9.5: `pid1-disk-size-bytes "wd0"` returns 4194304000 exactly,
  matching the v0.9.5 verify receipt's signature.
- v0.9.6: `services/journal-tail.el` requires cleanly under
  `GEOS_KERNEL=hurd`. no error, `journal-tail` feature present,
  transitive deps for journal-buffer/supervise satisfied.
- v0.9.7 dmesg-prime: prime ran once at journal-tail load time (4865
  bytes into `*journal*`); the explicit re-call doubled to 9730 bytes
  (delta 4865), matching the doubling-by-design contract recorded in
  the v0.9.6 dmesg-prime verify receipt.
