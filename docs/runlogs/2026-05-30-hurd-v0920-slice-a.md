# 2026-05-30 v0.9.20 slice A, GEOS_PID1=1 env splice + predicate OR-check

Continuation of docs/runlogs/2026-05-24-hurd-v0919-image-reroll-fullchain.md.
v0.9.20 ships slice A only.  Slice A closes a supervised-autostart
regression that has been masked on STATIC=1 PORT=hurd builds since
v0.9.16.  The regression sat behind one elisp predicate, `pid1-as-emacs-p`
in emacs-init/early-init.el, which keyed off `(getenv "PID1_MODULE_PATH")`.
On STATIC=1 builds pid1 never sets that env var (the module is inlined,
there is no .so to dlopen, so there is no path to advertise), so every
downstream supervision wiring guarded by that predicate silently no-op'd.
The Hurd v0918 image runs STATIC=1, so this is exactly where the
autostart gap lived.

## Result

PASS on the load-bearing claim.  The predicate now returns t under both
linkage modes.  Under STATIC=1 PORT=hurd the supervisor emacs sees
GEOS_PID1=1 in its environment at startup, early-init.el takes the
PID-1 branch, and the downstream supervision wiring fires the way it
already does under dynamic-module Linux dev hosts.  Slice A is a
shared-abstraction change, not a port_caps slot, so HURD_PORT.md has
no row flips this release.

What is not verified in this receipt: end-to-end autostart of the full
supervisor tree on a freshly re-rolled v0920 Hurd image.  Slice B (bake
the full 35-file canonical init.args into iso-build/hurd-image-reroll.sh)
was written this cycle then reverted before tag because it depends on
a v0920 image, and the v0920 image hit an independent rumpdisk wd0
enumeration race that wedges cold boot at `ext2fs: part:2:device:wd0:
No such device or address`.  The race triggers with or without
-snapshot, so it is real, not a QEMU snapshotting artifact.  Slice B
re-opens as task #220 under v0.9.21 once task #223 (wd0 settle gate
plus fail-fast smoke step in the re-roll) lands.

## What this slice ships

- pid1/emacs-init.c: file-scope `const char *geos_pid1_env =
  "GEOS_PID1=1";` plus a single envp[] slot at the supervised-emacs
  spawn site.  envp cap bumped 12 -> 13 to keep the NULL terminator
  honest.  No other call site touches the env vector.
- emacs-init/early-init.el: predicate body changes from
  `(getenv "PID1_MODULE_PATH")` to
  `(or (getenv "PID1_MODULE_PATH") (getenv "GEOS_PID1"))`.  The
  PID1_MODULE_PATH arm stays first so dynamic-module Linux dev hosts
  keep their existing path with no behavior delta.
- emacs-init/early-init.el: the predicate docstring grows a leak note.
  GEOS_PID1=1 propagates to every child of the supervisor emacs
  (eshell, make-process, shstub bounce-back).  A subprocess seeing
  GEOS_PID1=1 in its env does NOT mean it IS the supervisor.  Any
  future supervisor-identity check has to compare against a pinned
  pid token (e.g. `(= (emacs-pid) pid1-supervisor-pid)`), not this
  predicate.
- iso-build/hurd-fast-iterate.sh (main/9178dd1, landed earlier in
  cycle): tar-over-ssh push of emacs-init/ to a booted v0918 VM plus
  a supervisor bounce.  Cuts elisp-only iteration from ~20 min for
  the full image re-roll to ~5 s.  Not load-bearing for slice A, but
  it is why slice A landed in one sitting instead of three.

## Build matrix

Linux dev host: `make -C pid1` -> emacs-init built, no warnings,
envp[13] slot count matches the spawn-site write.

Hurd VM: `make -C pid1 PORT=hurd STATIC=1` -> emacs-init statically
linked, geos_pid1_env symbol resolves at file scope, no relocation
warnings.

## Probe run

```
$ ssh -p 2269 root@127.0.0.1 'cat /proc/$(pidof emacs)/environ | tr "\0" "\n" | grep -E "^(GEOS_PID1|PID1_MODULE_PATH)="'
GEOS_PID1=1

$ ssh -p 2269 root@127.0.0.1 'emacsclient --eval "(pid1-as-emacs-p)"'
t

$ ssh -p 2269 root@127.0.0.1 'emacsclient --eval "(getenv \"GEOS_PID1\")"'
"1"

$ ssh -p 2269 root@127.0.0.1 'emacsclient --eval "(getenv \"PID1_MODULE_PATH\")"'
nil
```

PID1_MODULE_PATH is nil on the STATIC=1 build (expected, the .so
does not exist on this image).  GEOS_PID1 is "1" because pid1 spliced
it at spawn.  The predicate returns t.  Before slice A, the same probe
on the same image returned nil and the autostart wiring silently
no-op'd.

## Open follow-ons (do NOT block this slice's commit)

1. hurd-essentials autospawn.  Slice A makes the predicate honest on
   STATIC=1, but hurd-essentials still runs only when its `add-hook`
   fires at the right phase of early-init.  Confirm under a v0921
   image that the hook fires without manual `M-x` poke.  Next-step
   hint: add a marker to /var/log/geos-boot.log from inside
   hurd-essentials-register and grep for it on a clean boot.

2. /var translator detach at boot.  Observed on the v0918 image
   pre-slice-A, suspected unrelated to slice A but unverified under a
   fresh v0920 image (see slice B blocker).  Re-test once task #223
   stabilises wd0 enumeration.  Next-step hint: capture
   `showtrans /var` and `df /var` from the first 30 s of boot, before
   any user login.

3. install slice C deployment gap.  v1.x install slice C was a
   one-elisp-line kernel-gate relaxation, but the deployed
   install.el on the v0918 image still pre-dates that change.  Folded
   into the next re-roll cycle.  Next-step hint: bump the embedded
   snapshot SHA in iso-build/hurd-image-reroll.sh after task #223.

4. Task #220, slice B re-open.  Bake the 35-file canonical init.args
   into the re-roll script.  Gated on task #223.  Next-step hint:
   land #223, re-roll, then this is a script-only diff.

5. Task #223, rumpdisk wd0 settle gate + fail-fast smoke step in
   the re-roll script.  The wedge looks like a translator-init race,
   not a content bug.  Next-step hint: insert a bounded retry around
   `settrans /dev/wd0` and a `ls -l /dev/wd0` smoke check before the
   re-roll declares success.
