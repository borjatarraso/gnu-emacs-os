# 2026-05-21: v0.9.6 journal-tail Hurd kmsg end-to-end VM-verify on Debian Hurd 0.9

this receipt is the live-verify pass for the v0.9.6 ship at `main/47d4bc1`:
the elisp wiring of `services/journal-tail.el` Hurd arm to
`tail -F --lines=+1 /var/log/kern.log`, the new
`journal-buffer--parse-syslog-record` parser in `buffers/journal.el`, and
the matching `freeze-test-hurd-kmsg-source.el`. this is the journal/native
kmsg slot from the v0.9 deferral list. it follows the v0.9.5 verify
receipt at `docs/runlogs/2026-05-20-v095-disk-size-verify.md` in shape and
tone, and intentionally does not touch `pid1/port_hurd.c`; the whole
slice lives in elisp on top of the existing supervise + journal stack.

## Verdict

PASS. the elisp pipeline is verified end-to-end on Debian GNU/Hurd 0.9:
`supervise-start` spawns `tail -F --lines=+1 /var/log/kern.log`, the
`--lines=+1` backlog replays through `journal-tail--filter-syslog`, the
filter parses syslog-format lines into the documented plist shape, and
the records render into the `*journal*` buffer with the
`HH:MM:SS source sev  msg` row format. probe H confirms it with both a
backlog replay and a live append landing in `*journal*` within one
sleep-for cycle. the three freeze-test asserts all pass.

one caveat, pinned clearly. this specific Debian Hurd 0.9 snapshot's
`/var/log/kern.log` is 0 bytes, because the boot-time gnumach printfs land
in `/var/log/dmesg`, read directly out of the gnumach printbuf by
`dmesg(8)`, not via `/dev/klog -> syslogd -> kern.log`. the pipeline
under test works; the upstream producer on this image is quiet. on a
system where runtime kernel events do flow through `/dev/klog` into
syslogd's kern.* sink, the same wiring would carry them. nothing in
the slice changes shape for that case.

## VM build environment

```
uname:           GNU geos-hurd 0.9 GNU-Mach 1.8+git20260224-up-amd64/Hurd-0.9 x86_64 GNU
debian_version:  forky/sid
emacs:           GNU Emacs 30.2
tail:            /usr/bin/tail, tail (GNU coreutils) 9.10
syslogd:         /usr/sbin/syslogd --no-forward (inetutils-syslogd)
```

`tail -F --lines=+1` is the exact command shape the journal-tail Hurd
arm registers. coreutils 9.10 supports both `-F` (retry on truncate /
rename) and `--lines=+1` (start at line 1, i.e. full backlog) in one
invocation. no busybox shim under it.

## Probe A: boot sanity

probe A confirms `/usr/bin/tail` exists with the right version, the
syslogd process is up with the documented `--no-forward` flag, and
`/var/log/kern.log` exists as a 0-byte file owned by root. emacs 30.2
is present. nothing surprising.

## Probe B: syslog topology

`/etc/syslog.conf` has the expected `kern.*  -/var/log/kern.log` rule,
so syslogd is in principle wired to drop kern.* records into the file
the elisp arm tails. `/var/log/` shows kern.log at 0 bytes, alongside a
populated `/var/log/dmesg` (3584 bytes, fresh from this boot) and a
populated `/var/log/syslog` (5131 bytes). `/dev/klog` is present as a
character device. no rotated `kern.log.*` files exist, so the 0-byte
size is not the result of a rotation.

## Probe C: kernel event trigger attempts

attempts to provoke gnumach into emitting through `/dev/klog`:
`dd if=/dev/cd0` and `dd if=/dev/fd0` both fail with
`No such device or address` (this QEMU has no CD or floppy attached),
`dd if=/dev/wd0` fails with `Invalid argument` (the storeio refuses
arbitrary reads outside aligned slices). `kern.log` stays at 0 bytes
across the burst. `dmesg` does show fresh `cd0: dos partition I/O
error` lines, which confirms that the gnumach printbuf is moving; it
just is not relayed through `/dev/klog -> syslogd -> kern.log`.

## Probe D: logger -p kern.info injection

`logger -p kern.info "geos v096 probe: synthetic kern.info"` and the
matching `kern.warning` variant both succeed at the shell level, but
inetutils-syslogd downgrades them to `user.notice` (a known
inetutils-syslogd behavior when the caller is not in the kernel
facility itself) and routes them to `/var/log/syslog` only. `kern.log`
stays 0 bytes. the syslog facility downgrade is not something the elisp
slice is responsible for or can work around.

## Probe E: direct /dev/klog write

`echo > /dev/klog` does not propagate either. `lsof` is not installed
on the image so I could not enumerate readers of `/dev/klog` to confirm
that syslogd holds the read end. the bottom line is the same as probes
C and D: on this image, nothing produces kern.* records that syslogd
relays to `/var/log/kern.log`.

## Probe G: freeze-test asserts and registry shape

probe G is the batch verify: load `core/port.el`, `services/supervise.el`,
`buffers/journal.el`, `services/journal-tail.el`, and
`freeze-test-hurd-kmsg-source.el`, then run the three asserts. all three
pass:

```
geos-kernel=hurd linux-p=nil hurd-p=t
state-* hard-stubbed
supervise loaded
journal.el loaded; provides journal-buffer? t
journal-tail loaded; registry has 1 entries
freeze-test-hurd-kmsg-source loaded

=== freeze-test-hurd-kmsg/* ===
service-command-under-hurd => pass
parse-syslog-good           => pass
parse-syslog-bad            => pass
```

the registered service shape matches the spec verbatim:

```
name=journal-kmsg
command=("tail" "-F" "--lines=+1" "/var/log/kern.log")
filter=journal-tail--filter-syslog
autostart=t
buffer=" *supervise:journal-kmsg*"
restart=on-crash
```

the parser was exercised against real on-disk data. since `kern.log` is
0 bytes, `kern.log line=nil` and `kern.log rec=nil`, which is the
documented "empty source" shape. the same parser run against the first
line of `/var/log/syslog` yields the expected plist:

```
syslog first line="Mar 14 22:32:15 debian syslogd (GNU inetutils 2.7): restart"
syslog first rec=(:source syslog
                  :time (27061 57839)
                  :sev "info"
                  :msg "syslogd (GNU inetutils 2.7): restart"
                  :raw "Mar 14 22:32:15 debian syslogd (GNU inetutils 2.7): restart")
```

and the last line:

```
syslog last line="May 20 23:17:02 geos-hurd CRON[813]: (root) CMD (cd / && run-parts --report /etc/cron.hourly)"
syslog last rec=(:source syslog
                 :time (27150 13022)
                 :sev "info"
                 :msg "CRON[813]: (root) CMD (cd / && run-parts --report /etc/cron.hourly)"
                 :raw "May 20 23:17:02 geos-hurd CRON[813]: (root) CMD (cd / && run-parts --report /etc/cron.hourly)")
```

`:time` is an emacs internal time pair, `:sev` defaults to `"info"` for
bare syslog records (the rfc3164 prefix on these lines has no priority
tag), `:msg` is the post-host portion, `:raw` is the verbatim source
line for round-trip auditability. this matches the parser's docstring.

probe H is the load-bearing pass. with the registered service spec from
probe G in hand, drive `supervise-start` and observe the `*journal*`
buffer.

step 1, seed kern.log with one synthetic baseline line so `tail -F` has
something to backlog:

```

```

step 2, spawn the registered service. `supervise-start` does not raise,
tail comes up with pid 973, the service flips to `running`, the buffer
slot is bound, and `process-live-p` returns t:

```

before start: status=stopped pid=nil
after start:  status=running pid=973 buffer=#<buffer  *supervise:journal-kmsg*>

```

step 3, wait for the `--lines=+1` backlog replay to land. the buffer is

```

*journal* head (max 600c):
---
01:30:00 syslog info  vmunix: v096 probe baseline

```

step 4, append a fresh synthetic line to `/var/log/kern.log` from
outside emacs and verify it lands live via `tail -F`'s follow:

```
===> append a fresh synthetic kern.log line and watch it land
*journal* after append, tail (last 400c):
---
01:30:00 syslog info  vmunix: v096 probe baseline
01:31:00 syslog info  vmunix: v096 LIVE probe synthetic event
```

both lines render as `HH:MM:SS source sev  msg`, source is `syslog` (the

the producer caveat from the verdict, not a defect in the pipeline.

teardown via `supervise-stop` runs clean.

## Runtime kern.log gap

worth saying twice in different words. the elisp wiring is correct per
spec: `tail -F --lines=+1 /var/log/kern.log` with
`journal-tail--filter-syslog` and `:restart on-crash`. probe H proves
the pipeline carries both a backlog seed line and a live appended line
all the way into `*journal*` with the expected render. what does not
happen on this specific Debian Hurd 0.9 image is upstream production:

1. gnumach's boot-time printfs go into the gnumach printbuf, which
   `dmesg(8)` reads directly via a mach RPC against the kernel. that
   path bypasses `/dev/klog` and syslogd entirely. that is why
   `/var/log/dmesg` is populated and `/var/log/kern.log` is not.
2. runtime errors from in-kernel device drivers (e.g. `cd0: dos
   partition I/O error` from probe C) also land in the printbuf, same
   bypass.
3. `logger -p kern.info` from userspace gets the kern.* facility
   downgraded by inetutils-syslogd because the caller is not in the
   kernel facility itself, so it never matches the
   `kern.*  -/var/log/kern.log` rule.
4. direct writes to `/dev/klog` from a non-kernel sender do not
   propagate to syslogd's kern sink either.

on a system where a real kernel-facility producer relays into syslogd
(or where the v0.9.6 wiring is later pointed at `/var/log/dmesg`
instead, which is a one-line :command change), the same supervised
tail would carry those events. that swap is out of scope for this
verify and shows up in the follow-on list.

## Leak smoke

100 back-to-back `journal-buffer--parse-syslog-record` calls inside a
single emacs process, with `/proc/self/status` captured before and
after the burst:

```
=== leak smoke: 100x parse-syslog-record ===
VmSize before=4541140 after=4541140 delta_kb=0
ports before=nil after=nil delta=nil
```

VmSize delta 0 across 100 calls. the mach port counter is nil because
Debian Hurd 0.9's procfs does not expose `/proc/<pid>/port_obj`, so the
runner's introspection path returns nil for both before and after. that
is expected and is the same gap the v0.9.5 receipt called out for the
disk-size slot's leak-smoke. the parser allocates nothing more than the
plist itself and one substring per match group, all of which gc cleans;
no Mach traffic, no external process spawn per call. this is parity
with v0.9.5's leak section.
